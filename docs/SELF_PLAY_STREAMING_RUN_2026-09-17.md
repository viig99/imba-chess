# Fresh ckpt34 streaming self-play

The new experiment uses the shared Lichess monthly source, training month window,
column projection, Elo/time-control/BOT filters and full-game parser. Search and
learning settings remain 128 simulations, top-m 16, depth 32, learning rate 1e-5,
reuse 2, 50,000 replay positions and 24 concurrent games.

Each shuffled group of four launched games contains one initial-board start and
one human takeover from each of plies 1–30, 31–70 and 71–120. The human sampler
requests the bucket first, then takes a uniformly selected eligible ply from a
fresh source game. Too-short games are skipped for that requested bucket. Human
sources assigned to the existing monitoring hash split are excluded entirely.
The saved monitoring manifest remains fixed for comparable screens; it no longer
supplies training starts. Human outcomes and Stockfish annotations are not labels.

## Streaming and recovery

`LichessDataset.filtered_shuffled_rows(filter_rows=False)` exposes the existing
raw monthly source to the self-play adapter. The adapter applies the same
`_game_filter` predicate before parsing. The normal supervised path is unchanged.
This small distinction is required: tests found that the installed HF filtered
Arrow iterator resumed at the wrong row inside a batch. Its raw iterator passed
the exact-resume tests. HF also explicitly does not preserve shuffle buffers.

The producer therefore shuffles blocks of 10,000 filtered rows with deterministic
per-block RNG and publishes immutable blocks of prepared starts with the raw
upstream cursor. This is block shuffling, not the identical HF rolling-shuffle
ordering. One persistent background process prepares two blocks ahead of the
furthest requested bucket. Independent bucket cursors retain all prefetched
starts. Published blocks are retained on disk as recovery history; ready input
prefetch is bounded, while historical disk storage grows with consumed data.

`stream/consumer.json` journals each launch before the game begins. Completed
launches are acknowledged only after replay flush; on restart, already committed
games are reconciled against replay, while outstanding launches are reissued in
sequence with identical IDs and seeds. Prefixes rejected by administrative game
limits are explicitly counted as retired. Interrupted launches remain retryable
while the same collection phase is active. If a phase already met its position
target, any remaining unsuccessful launches are explicitly retired at transition.

The stream journal is durable independently of the model checkpoint. Backups must
include `stream/` alongside checkpoints and replay. Missing journal state on
resume is an error, not permission to rewind the source. An unpublished partial
producer block may be read again after interruption; published source progress is
not restarted from the beginning. Workers have bounded terminate/kill cleanup and
a parent-death signal to prevent orphaned downloads.

## Verification

- 62 focused tests passed across self-play, stream cursor recovery, filters,
  producer restart, sampler launch recovery, deadline selection, configuration,
  existing nightly supervision and monitoring.
- The real input stream prepared 6,713 human starts (2,238 / 2,238 / 2,237) from
  10,000 filtered rows in 41.16 seconds. Worker shutdown took about 0.06 seconds.
- A CUDA initialize/resume smoke run used the actual 24-game collector and
  128-simulation search. Only the fresh-position threshold was reduced to 64 to
  exercise phase transitions quickly; actual completed collections had 2,537 and
  2,583 positions because active games drain before training.
- All 51 smoke games completed; start buckets were 12 / 13 / 13 / 13, with 39
  distinct human sources. Training advanced from zero to 8, then 17 optimizer
  steps after resume. Initial model tensors exactly matched ckpt34 after stripping
  the original checkpoint's compile-wrapper name prefix.
- Stream block-read/wait overhead was 0.025 and 0.031 seconds for the two smoke
  processes, with no retired starts. Collection rates included initialization and
  draining and were about 74k and 79k searched positions/hour; these short runs
  are correctness checks, not warmed-up nightly throughput estimates.
- Independent producer restarts in the smoke and full run generated byte-identical
  second remote blocks, including the upstream cursor (SHA256 checked).

Raw evidence: `artifacts/self_play_validation/streaming_smoke_2026-09-17/verification.json`,
`initialize.log`, `resume.log`, plus `metrics.jsonl` and `stream/producer.log`.

## Operation

Run directory: `artifacts/self_play/ckpt34-streaming-2026-09-17`.
Its `operation/` contains frozen base/run configs, monitoring seeds and systemd
unit definitions. The initial checkpoint is
`artifacts/checkpoints_v4/best_hr10_checkpoint_34_hr10=0.9677.pt`.
This starts with a fresh self-play optimizer/replay; it does not continue actor204.

`scripts/run_streaming_self_play_nightly.py` initializes once, then resumes on
subsequent nights. It chooses the next 08:00 America/Toronto deadline. Collection
launches stop 15 minutes before that deadline and get up to 10 minutes to drain;
training can checkpoint before the absolute cutoff. Recovery checkpoints are
written hourly and at phase boundaries. Strength screens are observed every
three hours, without automatic rollback or promotion, matching the prior research
run. Heavy profiling is off. The existing once-per-minute rates monitor reports
games/hour, positions/hour and optimizer steps/hour under `sessions/`.

The replacement `imba-self-play-streaming.timer` retains the previous September
scheduling horizon: 22:00 Toronto, September 17–30. The initial run is started
immediately; the 22:00 timer cannot duplicate an already active systemd service.
The old `imba-self-play-september.timer` is disabled when the new service is
activated. No old checkpoints or replay are removed.

Activated September 17 at 21:00:16 EDT. The service's recorded first-run deadline
is September 18 at 08:00:00 EDT. CUDA collection was confirmed active, and the
new timer was enabled after disabling the old timer. The operation launch manifest
records the ckpt34 SHA256 and implementation hashes used for this launch.

The first full cycle finished with 71 completed games, 7,569 training positions,
22 optimizer steps and `actor-000001.pt` saved. Buckets were 18 / 17 / 18 / 18,
with zero pending or retired starts. Input wait/read time was 0.028 seconds;
collection including final-game drain took 338.45 seconds (80.5k positions/hour).
The service advanced to iteration 1 collection and remained running.

Inspect with `systemctl --user status imba-self-play-streaming.service` and
`systemctl --user list-timers imba-self-play-streaming.timer`. Current metrics are
in the run's `metrics.jsonl`, human-readable output in `training.log`, and input
health in `stream/producer.log`.
